# Модель угроз IT-SERVICE-DESK (ЛР №6)

**Система:** IT-SERVICE-DESK (Symfony 7.4, PHP 8.4, Doctrine ORM, MariaDB, Twig, Bootstrap)  
**Область:** аутентификация, авторизация, работа с заявками, пользователями, сессиями и формами.  
**Дата подготовки:** 26.11.2026  
**Статус:** анализ и план проверок. Результаты автоматизированных тестов фиксируются отдельно после запуска.

## 1. Защищаемые активы и границы доверия

**Активы:** учётные записи и хеши паролей, персональные данные пользователей, заявки и их статусы, сессионные данные, права доступа, целостность БД и журналы ошибок.  
**Внешние границы:** браузер ↔ HTTP-контроллеры Symfony ↔ Security/Services ↔ Doctrine ↔ MariaDB. Входящие HTTP-параметры и поля форм недоверенные. Проверка прав должна выполняться на сервере, а не только скрытием кнопок в Twig.

## 2. Матрица угроз

| № | Asset (актив) | Threat (угроза) | Attack scenario (сценарий) | Mitigation (защита) | Test (проверка) |
|---|---|---|---|---|---|
| 1 | Данные пользователей и заявок | SQL Injection | Пользователь вводит SQL-фрагмент в поиск пользователя или параметр фильтра | Doctrine ORM/QueryBuilder и параметризованные запросы; запрет конкатенации пользовательского ввода в DQL/SQL | Отправить строку `\' OR 1=1 --` в поиск; убедиться, что данные не раскрываются и запрос выполняется безопасно |
| 2 | Отображаемые записи и сессии | XSS | В название заявки или имя пользователя передаётся HTML/JS, затем отображается другим сотрудникам | Автоэкранирование Twig; избегать `|raw` для данных из БД; Content-Security-Policy как дополнительная мера | Создать тестовую заявку с `<script>alert(1)</script>`; убедиться, что тег показан как текст и скрипт не исполняется |
| 3 | Заявки и учётные записи | CSRF | Злоумышленник заставляет браузер авторизованного пользователя отправить POST удаления | CSRF-токен и проверка в контроллере; POST вместо GET для изменяющих операций | POST удаления без `_token` и с поддельным `_token` не должен удалять заявку; валидный токен допускается только при достаточных правах |
| 4 | Чужие заявки и администрирование | Broken Access Control / IDOR | ROLE_USER изменяет URL на чужую заявку или открывает `/users` | `access_control`, серверные проверки ролей, `TicketVoter` (`VIEW`, `EDIT`, `CHANGE_STATUS`, `DELETE`) | Тесты для ролей: 403 на запрещённые маршруты и операции; проверка чужого ID; 200 только для разрешённых действий |
| 5 | Сессия пользователя | Session Theft / Fixation | Перехват cookie либо повторное использование сессии после выхода | HTTPS в рабочем окружении, `Secure`/`HttpOnly`/`SameSite` для cookie, корректный logout, обновление идентификатора при входе | Проверить атрибуты cookie и недоступность защищённых страниц после logout; не записывать секреты в Session |
| 6 | Пароли, секреты, конфигурация | Credential Leakage | Пароль сохраняется как открытый текст, попадает в репозиторий или Session | `UserPasswordHasherInterface`, `.env.local` вне Git, скрытие паролей и секретов в логах и Session | Проверить хеш в БД, `.gitignore`, `git diff --cached`, поиск секретов в репозитории, отсутствие паролей в Session |
| 7 | Файловая система сервера | Unsafe File Access / Path Traversal | Попытка доступа к `.env` или PHP-файлам за пределами `public/` | Веб-корень — только `public/`; отсутствие небезопасных endpoint для произвольного пути; строгая валидация путей при будущей загрузке файлов | Попробовать запросы к `/.env`, `/../.env`, `/composer.json`; сервер не должен отдавать секреты; если файловых функций нет — отметить как потенциальную угрозу будущих ЛР |
| 8 | Ошибки приложения и личные данные | Information Disclosure | Исключения показывают путь к файлам, SQL, stack trace или чужие персональные сведения | `APP_DEBUG=0` вне dev, ограничение доступа к страницам, безопасные сообщения об ошибках, корректные 403/404 | Запросить чужие записи, неизвестные ID, неправильный вход в prod-like режиме; проверить отсутствие debug-стека и приватных данных |

## 3. Ролевой контур доступа

В IT-SERVICE-DESK роли адаптированы под предметную область: `ROLE_USER`, `ROLE_TECHNICIAN`, `ROLE_MANAGER`, `ROLE_ADMIN` (в исходном учебном примере роль продаж соответствовала `ROLE_SALES`). Иерархия: `ROLE_ADMIN` > `ROLE_MANAGER` > `ROLE_TECHNICIAN` > `ROLE_USER`.

Для контроля доступа используются `security.yaml` (`access_control` и `role_hierarchy`) и `TicketVoter`. В интерфейсе ссылки скрываются при недостаточных правах, но серверная проверка остаётся обязательной.

## 4. Принципы проверок

1. Использовать отдельную **тестовую БД** с именем, содержащим `_test`.
2. Проверить 302 для гостя на защищённых страницах, 200 для разрешённых и 403 для запрещённых действий; 401 возможен только при соответствующем типе аутентификации, не обязателен для `form_login`.
3. Не проводить тест удаления с поддельным CSRF на рабочей БД.
4. Не считать успешную проверку Twig доказательством серверной авторизации.
5. Зафиксировать команду запуска, фактический результат, найденные проблемы и исправления в журнале тестирования.

## 5. Итог

Модель охватывает 8 требуемых категорий угроз. **Она не доказывает, что каждый риск устранён:** окончательный статус определяется результатами функциональных и ручных проверок в тестовом окружении.
