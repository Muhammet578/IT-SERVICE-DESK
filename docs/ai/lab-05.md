1. Цель работы
Освоить Doctrine ORM на существующем проекте IT-SERVICE-DESK: создать ORM-сущности и связи между ними, применить миграцию, подготовить тестовые данные (Fixtures), выполнить выборки с QueryBuilder/DQL, вывести агрегированную статистику на Dashboard и реализовать постраничную загрузку списков.
Адаптация предметной области. Исходный учебный пример описывает клиентов, товары и заказы. В IT-SERVICE-DESK аналогичные технические приёмы применены к пользователям, заявкам, категориям, статусам и комментариям. Это адаптация задания, а не буквальная реализация модели заказов.

2. Исходное состояние и сохранение совместимости
Ранее проект содержал реализацию на чистом PHP (лабораторные № 1–2) и Symfony-часть с контроллерами, формами, шаблонами и сервисами каталогов на DBAL (лабораторные № 3–4). В пятой лабораторной новый функционал реализован с Doctrine ORM; старые маршруты просмотра и формы не переписывались полностью.

Чтобы избежать повреждения прежних данных и конфликтов схемы, для новой ORM-модели использована отдельная локальная база it_service_desk_orm. Прежняя it_service_desk сохранена. Подключение задаётся через локальную переменную DATABASE_URL (секретные параметры не размещаются в Git).
3. ORM-сущности и связи
Созданы семь сущностей в symfony-app/src/Entity/:
Сущность	Назначение	Основные связи
Role	Роли пользователей	Одна роль — много пользователей
User	Пользователи системы	Многие пользователи — одна роль; автор и/или исполнитель заявок
Ticket	Обращения в поддержку	Ссылки на автора, исполнителя, категорию, приоритет и статус
Category	Категории заявок	Одна категория — много заявок
Priority	Приоритеты	Один приоритет — много заявок
Status	Состояния заявок	Один статус — много заявок
Comment	Комментарии к заявкам	Многие комментарии — одна заявка и один пользователь


Связи оформлены атрибутами Doctrine (#[ORM\Entity], #[ORM\ManyToOne], #[ORM\JoinColumn] и др.). Наличие внешних ключей поддерживает целостность данных на уровне СУБД. Для исполнителя допускается отсутствие назначения (assigned_to — nullable).

Fixtures предназначены для разработки и демонстрации. Команда doctrine:fixtures:load по умолчанию может очищать существующие таблицы — её не следует запускать на базе с нужными пользовательскими данными.

Основные команды для развертывания новой локальной БД (из каталога symfony-app):
php bin/console doctrine:migrations:migrate --no-interaction
php bin/console doctrine:schema:validate
php bin/console doctrine:fixtures:load --no-interaction
5. Репозитории и запросы
Для работы с ORM созданы/расширены репозитории:
- TicketRepository: получение заявок по статусу, автору и периоду; постраничная загрузка списка.
- UserRepository: выборка активных пользователей, рейтинг пользователей по количеству созданных заявок; постраничный список с поиском и сортировкой.
- CategoryRepository: рейтинг категорий по количеству заявок.
Используются QueryBuilder, параметризованные условия, агрегат COUNT, группировка GROUP BY, сортировка ORDER BY, ограничения setFirstResult() и setMaxResults(), а для подсчёта общего числа строк — Doctrine Paginator.

Для сортировки пользователей разрешены только поля id, name, email (белый список). Пользовательский поисковый текст передаётся через параметр запроса, а не включается непосредственно в SQL.
6. Dashboard и агрегированная статистика
Сервис symfony-app/src/Service/DashboardService.php собирает показатели из репозиториев и DQL; HomeController передаёт их в templates/home/dashboard.html.twig.

Выводятся:
1. Общее количество пользователей.
2. Общее количество заявок.
3. Количество незавершённых заявок (у статуса isFinal = false).
4. Количество завершённых заявок (всего минус незавершённые).
5. Среднее количество заявок на пользователя (ticketsCount / usersCount, с защитой от деления на ноль).
6. Пять пользователей с наибольшим числом созданных заявок.
7. Пять категорий с наибольшим числом заявок.
Агрегации выполняются на стороне СУБД, а контроллер занимается передачей готовых значений в Twig. Интерфейс оформлен с помощью Bootstrap.
7. Пагинация пользовательского интерфейса
7.1. Заявки: /tickets
TicketController::index() получает номер страницы из параметра page и запрашивает через TicketRepository не более 10 заявок. Шаблон templates/ticket/index.html.twig показывает общее количество записей и навигацию по страницам. Просмотр отдельной заявки (/tickets/{id}) сохранён.
7.2. Пользователи: /users
UserController::index() использует ORM-репозиторий и выводит не более 10 пользователей на странице. Сохранены поиск по имени/email, сортировка по id, name, email, а также параметры search и sort при переходе между страницами. Создание и редактирование пользователей продолжают использовать ранее разработанный UserCatalog/DBAL.

Отдельная страница /users/{id}/tickets не внедрялась: принято решение использовать существующие списки, а не дублировать интерфейс. Фильтрация заявок по автору может быть добавлена позднее, но не считается выполненной в этой работе.
8. Выполненные проверки и ограничения
Проверено вручную в ходе разработки:
- Миграция применялась успешно; Doctrine ранее подтвердил корректность схемы/маппинга.
- Страницы /tickets и /users с пагинацией работают по подтверждению разработчика.
- Dashboard с реальной статистикой работает по подтверждению разработчика.
Не выполнялось в рамках финализации:
- Отдельный набор из пяти unit/integration-тестов и пяти функциональных тестов, предусмотренный исходным заданием.
- Полный регрессионный прогон всех сценариев создания/редактирования на новой ORM-базе.
- Проверка всех краевых случаев при большом числе страниц и пустых результатах поиска.
Лабораторная демонстрирует реализованный функционал ORM, миграций, Fixtures, агрегатов и пагинации, но не может считаться полностью закрытой по требованию автоматизированного тестирования, пока указанные тесты отсутствуют.

10. Итог
В IT-SERVICE-DESK добавлена ORM-модель на Doctrine, применена миграция и настроены Fixtures. Реализованы запросы QueryBuilder/DQL, Dashboard с агрегированной статистикой и пагинация списков пользователей и заявок по 10 записей. Ранее существовавшие страницы и формы в основном сохранены.

Следующие возможные улучшения: фильтр заявок по автору/категории/статусу, интеграция форм с ORM, автоматизированные тесты, проверка регрессий старых DBAL-операций и доработка интерфейса.
